# Decisions (and where we deviated from the plan)

Each entry: what we chose, why, and what it replaced in [PLAN.md](PLAN.md).

### D1 · Native shell: WinForms + WebView2 via the in-box C# compiler, not Tauri
Tauri needs Rust, and on Windows that means the Visual Studio Build Tools, an admin install of about 6 GB. `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe` ships with every Windows 10/11 machine and can host the same WebView2 runtime, so `shell/build.ps1` builds `MIMI.exe` in seconds with no toolchain. The trade-off is that the shell is Windows-only; the web UI and Core are cross-platform.

### D2 · Core manages llama-server directly, not llama-swap
Core already supervises every other process. Doing model swaps itself gives the UI precise status ("Waking up Gemma 4 12B…") and one less binary to ship.

### D3 · Core terminates TLS itself, not Caddy
The share server is a second uvicorn listener with a certificate issued by a local CA that Mimi generates (`share.py`, using the `cryptography` package). mDNS (`mimi.local`) comes from `zeroconf`. That's one process fewer and no Go binary.

### D4 · OCR with RapidOCR (PP-OCRv6, ONNX), not Tesseract
It installs from pip with its models bundled, needs no admin rights, and is more accurate on photos. It reads a sign in about 0.5 s on the CPU.

### D5 · Places from GeoNames, not an OSM POI extraction
GeoNames for the US and Canada is small (a few hundred MB), and it has clean feature codes (parks, historic sites, lakes, summits) and populations. Geotagged Wikipedia adds the notable landmarks. Fuel stations and hospitals now come from OpenStreetMap, in a table of their own ([D17](#d17--fuel-stations-and-health-services-from-the-routing-extract-in-their-own-file)).

### D6 · Default model on the 16 GB reference device: Gemma 4 12B (QAT Q4_0)
We measured both finalists inside the real app (Chrome, the Claude app and Steam open):

| | Generation | Prompt | Grounded answer (2 turns) | Quality |
|---|---|---|---|---|
| Gemma 4 12B | 7.3–9.6 tok/s | ~110 tok/s | 36–39 s | Correct, well cited, clean |
| Qwen3.5-9B | 11–12.8 tok/s | ~110–150 tok/s | 42–49 s* | **Invented a 1975 first ascent and fake citations; leaked `<tool_code>` text** |

\*Qwen made extra, malformed tool calls. Gemma misses the plan's 8 tok/s bar by a little under memory pressure, but it was the only model that stayed accurate. For an offline reference device, accuracy beats speed. Qwen3.5-9B remains the Reader/alternative, Qwen3.5-4B powers voice and battery saver, and all three can be switched in Settings → Models.

### D7 · Forced grounding and a citation sanitizer
Small models skip the search and answer from memory, sometimes with invented citations. For questions that look factual, the first step now requires a tool call. Afterwards any citation that doesn't point to a real source is removed.

### D8 · Offline routing with Valhalla
The plan left routing out because OSRM needs more than 16 GB of RAM to build North America. Valhalla's Windows wheel (`pyvalhalla`) includes `valhalla_build_tiles.exe`. Its temporary disk use is about 5× the input, so `scripts/build_routing.py` first filters the OSM extracts down to drivable roads, ferries and turn restrictions with pyosmium. That cut the input to a third in testing. Routes compute in about 0.1 s.

### D9 · A library that isn't all of Khan Academy
Kiwix only publishes the full Khan Academy edition (about 180 GB), which doesn't fit next to Wikipedia with images, so it's an external-SSD item. Five TED topics (about 11 GB) and two Gutenberg shelves (about 3.8 GB) are included instead of the 16 GB English-literature shelf, to keep disk headroom.

### D10 · Title boost in library search
Xapian full-text ranking sometimes buries the article whose title *is* the topic ("Bee sting"), so search also looks up titles and boosts the one that is the topic.

The first version tried only the query's leading words, and dropped little words from the query but not from titles. So "Speed of light" or "Great Wall of China" could never match, while one-word titles such as "Since", "Capital" and "Ratio" did. On the F1 retrieval check (2026-10-20), the right article came first for 11.7 % of questions.

The lookup now works like this:
- **Runs:** it tries runs of one to four of the query's first six content words (a lone word needs four letters: "burn"), anywhere in the query, with the little words inside a run kept, all lengths at once, in the four largest books that aren't Q&A.
- **Matching:** a title counts when it appears in the query word for word, or without its own inner little words.
- **Redirects** are followed to the article.
- **Short titles:** a title that is only a small part of the question needs the full-text search to find that article too, unless it comes from a book on the question's subject (an intent prior above 1: "Hypothermia" in MDWiki for a medical question).
- **Count:** up to three different titles are kept, each from every book that has it, the ones the full text agrees with first. Counting each book's copy as a title, three books' "First aid" took every place for "burn first aid" and no burn article reached the model; keeping only the first copy dropped MDWiki's "Myocardial infarction" for Wikipedia's.

On the same check, the right article now comes first for 35.0 % of questions and is in the top 10 for 46.0 % (29.2 % before).

### D11 · Launch at startup is a Task Scheduler task, not a Run key entry
The plan used the per-user `Run` registry key. On the reference device, Explorer ran every other entry in that key at sign-in but silently skipped Mimi's (its Shell-Core log lists each command it starts; Mimi's never appeared, and nothing marked it disabled). The setting now registers a per-user task with a logon trigger (`schtasks`, no admin rights), set to run on battery, with no time limit and normal priority. Core re-syncs it at every start, which also moves an old Run entry over and re-points the task when a portable drive comes back under a new letter.

### D12 · Model and retrieval changes are backed by an eval run
D6 picked the default model from a few conversations, and the D7 sanitizer can't tell a real citation from a misattributed one. Changes to the default model, the system prompt, the tool loop or library search now come with a run of the golden set (`eval/run.py`, 166 questions across medicine, repair, travel, survival, general knowledge, location and adversarial prompts) and a scoreboard from `eval/score.py`. The scoreboard covers key-fact accuracy, forbidden claims, answer/hedge/refuse behavior, citation faithfulness (`mimi.grounding`, which checks each `[n]` against its source and flags invented numbers, swapped names and contradictions), Recall@k/MRR and latency. Model comparisons are A/B runs on the same device in the same session, with a McNemar test on per-item flips, and safety metrics are read first (see [EVALUATION.md](EVALUATION.md)). Gemma 4 12B now has full English and Spanish runs on the F1 (2026-10-20, in `eval/reports`). The A/B against Qwen3.5-9B that would confirm or overturn D6 hasn't been run, so D6 stands on the side-by-side sessions above. The plan had no evaluation step.

### D13 · An honest library: survey every book, list what JavaScript would have listed
A user opened the Medical Library and got a blank page. The `zimgit-*` ZIMs (medicine, water, knots, food, post-disaster) are built by nautilus: the home page is an empty `<ul id="doc-list">` that JavaScript fills from `database.js`, and the content is PDFs under `files/` (12 in medicine, 7 in water). Mimi's reader strips scripts, as it must, so it showed "Loading… No result for this search request". The Kiwix catalog says "1 article", and Xapian only indexed the home page (a search for "bleeding" found nothing), so chat could never cite these books either.

Core now surveys each book in the background (`KiwixClient.survey`): it fetches the main page and recognizes nautilus (`doc-list`/`nautilus.js`), TED (`video-items`; talks in `assets/data_<lang>.js`, or `assets/data.js` in older ZIMs) and Gutenberg (`full_by_popularity.js` rows of `[title, author, formats, id, shelf]`; cover pages at `<title>_cover.<id>`, with `.html` before gutenberg2zim 3). The data files are parsed as literals, never run. The library then lists their items natively, opens PDFs in the browser's own viewer and plays media with `<video>`/`<audio>`.

The same pass is a health check. A book is *readable* if its main page has real content (200+ characters or 8+ links once cleaned) or its item list isn't empty. It is *searchable* if it carries `_ftindex:yes`, or a probe search finds something other than its home page, or (for document collections) its PDFs are in our text index. Cards show this as Ready, Indexing…, Browse only, Search only or Can't open, with a plain-English note. Item counts are honest ("12 documents", not "1 article"). The findings are stored with the ZIM's UUID, so the next start shows them at once.

### D14 · Library ranking: rank fusion, intent priors, optional semantic rerank
Xapian scores aren't comparable across books, our PDF index has its own BM25 scores, and the old search simply concatenated per-language groups, so Stack Exchange's many short posts often crowded out WikiMed. `retrieval.py` (pure functions, unit-tested with fakes) now does the ranking:

- **Reciprocal-rank fusion** over the title lookup (weight 2, up to three titles; see D10), the PDF-page index and each Xapian group. A multi-book Xapian result is split per book first, so each book's best hit starts level. K = 10 rather than the textbook 60, because our lists are short (≤ 20) and K = 60 flattens them until only the priors matter.
- **Intent priors**: a cue-word classifier (medical, repair, survival, travel, tech, define) multiplies scores per collection, within about ×0.45–×1.5. "How do I stop bleeding" lifts Medicine (WikiMed, the medical PDFs) above Q&A, and "replace a cracked screen" lifts iFixit. With no intent, Q&A starts at ×0.85.
- **Semantic rerank (optional)**: when the bge-m3 embedding server is *already running*, the top 20 candidates' title + snippet are embedded with the query in one call and blended 50/50 (min-max normalized) with the fused score. Search never starts the server (that costs RAM and seconds); a failed or slow call falls back to the fused order and isn't retried for 20 s.
- **Passages**: paragraphs are scored with BM25 over the lightly stemmed words of the model's query and of the user's own question (IDF from the article's own paragraphs, title words damped), plus credit for a matching section heading or intent synonym ("treat" → Management). When embeddings are up, the best 8 are blended 60/40 with embedding similarity. A PDF passage is drawn from the cited page, plus the next page only where it is relevant, and the citation says "pp. 111–112" when it uses both.

Latency budget, per library search: Xapian groups and the title lookup run in parallel. The lookup sends up to 18 suggestions to each of 4 books plus a redirect check for each of up to 10 matching titles, which is why kiwix-serve gets up to 8 threads. On the F1 a search measured a median of 0.5 s with the model at its fallback settings. With the full-context model loaded it took about 1 s, because Windows' file cache was down to 0.1 GB, so most reads went to disk. The FTS5 page query takes under 10 ms (measured 1–10 ms on 3,400 indexed pages); fusion takes under 1 ms. The optional rerank is capped at 1.2 s and each passage's embedding at 0.8 s. With the embedding server down, ranking adds about 10 ms; the worst case adds about 2 s.

### D15 · PDF text lives in a separate, rebuildable SQLite cache, extracted out of process
Extracted text is a cache of the ZIMs, not personal data, so it goes in `data/library-index.sqlite` rather than a `mimi.db` migration. It can be deleted at any time, it stays out of backups of personal data, and bulk inserts never hold the chat database's lock. The FTS5 table uses the Porter tokenizer; rows are keyed by ZIM name, path and page, and keep the PDF's printed page label ("Where There Is No Doctor" physical page 312 is printed page 265; physical page 50 is page 3 after the w1–w32 front section). A label table with repeats can't identify a page, so then physical numbers are used. Page 0 of each document holds its title, author and description, so videos and scans are still found by title. A document is re-read only when its ZIM's UUID changes.

pypdf is pure Python, so extraction runs one document at a time in a below-normal-priority worker process (spawned, as on Windows) instead of a thread that would hold Core's GIL. The two sample libraries (19 PDFs, 3,444 pages) took about 75 s on the first start and 12.5 MB of index; nothing is redone on later starts. PDFs over 200 MB and pages beyond 3,000 are skipped.

### D16 · ZIM content is untrusted: sandbox it, and only frame PDFs
`render_reader` output is rendered with `{@html}`, so it keeps only http(s)/mailto links (made inert), relative links and in-ZIM media. Every other URL scheme is removed: `javascript:`, `vbscript:`, `data:` (except `data:image/` in `<img>`), `file:` and the rest, including disguised forms like `java\tscript:`. It also drops `iframe`, `object`, `embed`, `form` and `base`, and removes duplicate namespaced attributes (an SVG `<a>` with both `href` and `xlink:href`). The `/kiwix` proxy serves ZIM HTML, SVG and scripts with `Content-Security-Policy: sandbox`, so a ZIM page opened directly can't act with Mimi's origin and cookies. PDFs and media get `frame-ancestors 'self'` so the reader can show them in an iframe; nothing else can be framed.

### D17 · Fuel stations and health services from the routing extract, in their own file
"Where's the nearest gas station?" and "closest hospital" had no data to answer from: GeoNames has no fuel stations and only a thin, partly historical list of hospitals (D5). The OpenStreetMap extract the routing pack already downloads has them. `scripts/build_geodata.py --only pois --osm <extract>` reads it with pyosmium and writes `maps/pois.sqlite`: amenity=fuel, amenity/healthcare=hospital, amenity/healthcare=clinic, amenity/healthcare=pharmacy and emergency=ambulance_station, with the name, a point (areas and multipolygons: the mean of up to 16 of their nodes), the OSM id and the useful tags as JSON (opening_hours, phone or contact:phone, brand, operator, emergency yes/no, the addr:* parts, fuel:* yes/no). access=private or no is left out, and so are doctors' offices and defibrillators: they are many, and none of the agreed UI kinds. A place mapped twice (a hospital campus and its main building, a fuel station's node and its bare canopy) is merged when kind and name match within 40-400 m depending on the kind. An unnamed one joins a named neighbor only within half that and only when it has no address or phone of its own. Two same-brand stations 75 m apart in Andorra stay two.

It is a separate file, not more rows in `places.sqlite`, for three reasons:

- **Licenses.** `places.sqlite` is GeoNames (CC BY 4.0). OSM data is ODbL, whose share-alike applies to a database derived from it. Two files keep each one's terms plain.
- **Lifecycle.** Places are built in the Lite tier from GeoNames; the extract only exists in the routing pack (Standard). A separate file is built when the extract is there and needs no rebuild of the 400 MB places database. An older `places.sqlite` keeps working unchanged.
- **Ranking.** Places are ranked by how notable they are; services are wanted nearest first. Kept apart, the "all" query stays as it was (a fuel station never crowds out a national park), and service queries never pay for the notability scoring.

`GeoData.nearby` takes the service kinds as stable ids (`fuel`, `hospital`, `clinic`, `pharmacy`, `ambulance`; `health` means the medical four) and returns them nearest first. When nothing is inside the radius the search doubles it, up to 250 km: the nearest hospital is worth knowing even when it is 60 km away. The file records the area its extracts cover (their header box, else the extent of their places plus 0.1°). Outside it, hospitals and clinics fall back on GeoNames (HSP, HSPC, HSPD) and say so, and the tool tells the model when the device simply has no such data, instead of "nothing found".

The cost is one more pass over the extract, plus a node pass per 2³¹ node ids (the same windowed IdFilter as the address build). That is seconds for a small country and minutes for US + Canada, inside a build that takes hours. Tested on real OSM data for Liechtenstein (Vaduz), Appenzell Innerrhoden, Monaco, Andorra, San Marino, Jersey and central Heidelberg: 268 places from 278 tagged objects, 10 merges, all checked by hand.

### D18 · One OpenStreetMap download per region, shared by the builds that read it
The routing build downloaded the Geofabrik extract itself and deleted it after filtering out the roads. The fuel/hospital table (D17) and, outside North America, the address index (D19) need the same file. Downloading it three times would cost up to 19 GB each for US + Canada, so the extract is now a first-class item in the content manager (`"type": "osm"` in `manifests/packs.json`): fetch.py downloads it once to `{cache}/osm/` (resumable, checked against Geofabrik's `.md5`), every build that names it (`"{osm}"` in its args, or `"inputs": ["osm"]`) reads that copy, and it is deleted once the last of them succeeds. If one fails, the file stays, so running the command again resumes.

The routing build used to free the raw extract before its disk-hungry tile build, which matters for US + Canada. It still does when it is the last reader. When a later build still needs the extract, fetch.py passes routing's `keep_inputs` flag (`--keep-download`). The Standard tier lists addresses before routing, so outside North America routing is last and peak disk use is what it was. The extract comes with the routing pack (and the addresses pack where addresses come from it). Lite, which has neither, downloads nothing new. An install that already has routing shows the pack as partly installed; `content add routing` downloads the extract again once to build the table.

### D19 · Street addresses outside the US and Canada from OpenStreetMap, without touching the US and Canadian keys
Regions marked `"addresses": "osm"` (UK, Germany, France, Australia, New Zealand) build `maps/addresses.sqlite` from the region's extract (`--osm-points` and `--osm-roads`, D18). Japan is left out: its addresses are numbered blocks, not house numbers on named streets, and OSM's Japanese data rarely has addr:street.

**Keys stay as they were.** `street_key` already keeps ß and folds accents, so "Hauptstraße" is keyed "hauptstraße" and "Rue de la Paix" "rue de la paix". Changing the normalization (for example ß to ss, or a German street-type table) would change some keys and force every US and Canadian index, a 45-minute build, to be rebuilt (`norm_version`). Instead the other spellings people type are tried as extra exact keys at query time (`address_norm.intl_variants`): ß and ss, "Str." for Straße/Strasse/straat, ae/oe/ue for ä/ö/ü, and leading abbreviations ("C/", "Av.", "P.zza", "V.le"). `VERSION` stays 2, and existing indexes keep working.

**Parsing by shape.** The parser recognizes international forms by their shape: a house number after the street when the name carries a European street word ("Hauptstraße 5", "Calle Mayor, 12", "Via Roma n. 1"), a postcode before the town in a later part ("10115 Berlin", "1012 AB Amsterdam", "AD500 Andorra la Vella"), and UK, Irish and Australian postcodes. It then rewrites the input as "number street, town" for the existing parser, with US state detection switched off. Input with none of these shapes is parsed exactly as before. All 62 US/Canada parser cases and every engine test pass unchanged. An index built from OSM alone (no TIGER, ZIP or NAR input) reads every query the international way, so "Städtle 23, Vaduz" (no street word) works there too.

**What the build adds for those indexes.** House numbers like "5a", "12bis", "5/1" and "16-18" (filed under both ends); addr:place where a hamlet's houses have no street; postcode centroids, plus UK districts ("SW1A") like Canadian FSAs; US state codes in addr:state ignored (Swiss "AR" is Appenzell, not Arkansas); and a `localities` table of the towns the addresses name (addr:city: centroid, spread-based radius, count). The table finds a town the gazetteer names differently ("München" where GeoNames says "Munich") and labels results in places GeoNames doesn't cover. Results are written the way their country writes them: "Hauptstraße 5, 10115 Berlin", "10 Downing Street, London SW1A 2AA" (`address_norm.number_first`, `postcode_first`).

Tested end to end on real OSM data: Vaduz, Appenzell Innerrhoden, Monaco, Andorra, San Marino, Jersey and central Heidelberg (26,874 address points, 5,409 streets). Whole-country extracts of the five regions have not been built yet, because Geofabrik wasn't reachable from the test machine. Coverage there is whatever OpenStreetMap has: near complete in Germany, patchy in parts of the UK, where few addresses are mapped.

### D20 · The USB image is mmdebstrap plus a shell script, not mkosi or a customized cloud image
A bootable stick has to be easy to audit and rebuild: anyone should be able to read what is on it and make the same thing on a GitHub runner. `scripts/image/build.sh` partitions a sparse disk image (BIOS boot, EFI system, a small FAT "MIMI" partition, root), installs exactly the packages in `scripts/image/packages.txt` with **mmdebstrap** (Debian's own tool, in Debian and Ubuntu, no Recommends), copies `scripts/image/rootfs/` over it, and runs `scripts/image/configure.sh` inside it. That script uses the normal `scripts/install.sh --tier none`, so the stick runs Mimi exactly as a Linux install does. Then the root filesystem is shrunk to its contents and the image is compressed with xz, which Rufus, balenaEtcher and `dd` all read. It needs root (loop devices, a chroot) and nothing newer than Ubuntu 22.04 provides.

Alternatives:
- **mkosi** is declarative and pleasant, but its configuration format has changed between releases, and Ubuntu 24.04 ships 20.2 while upstream is far ahead, so the result would depend on which mkosi and which host systemd built it. BIOS and shim support also differ between versions. Two shell scripts (about 480 lines with comments) use only `sfdisk`, `mkfs`, `mmdebstrap`, `mtools` and the boot loaders inside the image, and read top to bottom.
- **A Debian cloud image with virt-customize** starts from the cloud kernel, which lacks most PC hardware drivers and all firmware, and from cloud-init. Swapping the kernel, adding firmware and removing cloud-init is more work than starting minimal, and libguestfs is slow without KVM.

Choices inside the image:
- **An installed system on the stick, not a live image.** [PLAN.md](PLAN.md) imagined a live "Mimi OS" that leaves no trace. A live system forgets everything at shutdown, and Mimi's accounts, chats and tens of gigabytes of content have to persist, so the stick holds a normal read-write Debian. It still never touches the computer's own disks.
- **Boot**: GPT with a BIOS boot partition for GRUB's BIOS code, and for UEFI the removable-media path `\EFI\BOOT\BOOTX64.EFI` holding Debian's shim, which Microsoft signs, then Debian's signed GRUB and kernel, so Secure Boot can stay on. The EFI files are laid out by hand (what `grub-install --removable --uefi-secure-boot` does) and copied onto FAT with mtools, so the build never mounts FAT and works on hosts without it.
- **Growing on first boot**: the root partition has the GPT "root x86-64" type; `systemd-repart` grows it (two lines in `/etc/repart.d/`) and `x-systemd.growfs` in fstab grows ext4 online. No growpart script.
- **Screen**: cage (a Wayland compositor that shows one app full screen) running Chromium in kiosk mode. Chromium is the engine of the Windows shell's WebView2 and of the Playwright tests. A systemd service opens a PAM session for the `kiosk` user on tty1, which is the only automatic login; that user has no password and no shell, and there is no getty on any console. Core runs as a separate `mimi` user with `ProtectSystem=strict` and one capability (binding 443/80 when the owner turns sharing on).
- **Content isn't in the published image**: the tiers are 16–245 GB and release files max out at 2 GB. A timer runs `mimi content add lite` once the stick is online and restarts Core when it's done. Wi-Fi is set by filling in `wifi.txt` on the FAT partition, because Mimi's own settings can't join Wi-Fi on Linux and the FAT partition is the only part of the stick Windows and macOS can open. `--tier` bakes content in, for local builds only.
- **Boot test hooks ship in the image, inert**: QEMU passes a systemd credential (`mimi.boottest`) as an SMBIOS string; units with `ConditionCredential=` then forward port 7601 to Core and copy the journal to the serial port. CI therefore tests the exact file people download, and on a real PC nothing sets that credential, so those units never start.

### D21 · Books in the user's language are searched with the user's words, not through a translation
A Spanish or French book needs a query in its own language: Xapian stems and matches words, so "burn first aid" finds little in Spanish medical Wikipedia, and "quemadura primeros auxilios" finds *Quemadura*. The English books, which are most of any library, still need the English query. So `search_library` takes an optional second query, `local_query`: the model already writes the English one (a rule in the system prompt), and the same rule asks for the keywords in the user's language when they aren't writing English. Core sends each Xapian language group its own query, looks up titles in each language, where that language decides which words count as little (a title with little words inside it matches without them: "Picadura de abeja" for "picadura abeja"), and picks a Spanish article's best paragraph with the Spanish words.

If the model leaves `local_query` out (small models sometimes do), Core takes the content words of the user's own message instead. Which language counts as the user's: the one `i18n.detect` finds in the message, else the interface language.

Alternatives:
- **Translate the English query in Core** would need a translation model on the device, or a second model call per search, which costs seconds on the handheld.
- **One query in the user's language for everything** would break the English books, the ones that answer most questions.
- **Cross-language search with embeddings alone** (BGE-M3 is multilingual) only reranks what Xapian found; it can't find what the keyword search missed.

Tried on the real Spanish medical Wikipedia (469 MB) next to the English one with five first-aid questions: with the Spanish words, the right Spanish article came first or second every time; with the English words alone it was in the top four for two of the five, behind wrong matches such as *Celecoxib* for "anaphylaxis signs". The fallback (keywords from "¿Cómo trato una quemadura?") found *Quemadura* second, after the English *Burn*.

### D22 · A 12B model on a 16 GB handheld: bound every cache, and treat out of memory like a crash
On the F1, 16 GB of RAM leaves 12.8 GB to Windows, because 3 GB is carved out for the GPU. Gemma 4 12B with its context takes about 9 GB of that. The first full eval run (2026-10-19) crashed 20–80 minutes in, and a whole evening's runs ended up on a slow fallback. Three things were filling memory, and none of them was the model itself:

- **llama.cpp's prompt cache.** It keeps earlier prompts' state in RAM, 8 GB by default. Gemma's prompt state is about 3 GB, so the cache held one or two of them next to the model. `--cache-ram` is now 512 MB on devices up to 16 GB (2 GB up to 32 GB, the default above). On the F1 nothing is cached in RAM; the slot's own KV cache still reuses the shared start of each prompt.
- **kiwix-serve's search memory.** libkiwix held on to 28–70 MB per full-text search: 4.9 GB after 60 searches in a test, most of it paged out but all of it counted against the commit limit. A cache of two searches bounds part of it. The rest isn't bounded by any setting, so the library watcher restarts kiwix-serve with the same books once it holds more than 12 % of RAM, only while the library is idle. A restart takes about 3 seconds and costs the next search a cold start.
- **The V half of the KV cache stays f16, with q8_0 as a fallback rung.** An f16 V cache at an 8192 context ran out of graphics memory on a 3,500-token prompt even with nothing else running, so for one full English and Spanish run (2026-10-21) both halves were q8_0. That run was slower: the first word came after 24.4 s at the median instead of 16.0 s. In llama-server's log, every request that reused the cached prompt paid about 3 s more with a q8_0 V cache (a 40-token step took 4.5 s instead of 1.2 s), and a turn makes two or three requests. llama-bench hadn't shown it: it measures throughput, with no cached prompt, and was run with 12 layers on the GPU. So V is f16 again, and the fallback ladder gets a rung with a q8_0 V cache at the 4096 context before the one that leaves more memory free: at 4096 with 1536 MB kept free, q8_0 ran both 5-hour runs without a crash, where f16 had crashed once.

None of this stops other programs from taking graphics memory after the model has loaded. A browser or the lock screen was enough on the F1: llama-server then stayed up but failed every request. Core treats that the same way as a crash. It stops the model, restarts it one rung down the fallback ladder ([ARCHITECTURE.md](ARCHITECTURE.md#memory-and-models)), and asks the question again once. Before this, those turns ended with an empty answer and no error.

Alternatives:
- **A smaller default model** would leave room but answer worse. D6 chose Gemma for accuracy.
- **`GGML_VK_PREFER_HOST_MEMORY`**, putting all of llama.cpp's buffers in shared memory, kept the model from loading. **`GGML_VK_ALLOW_SYSMEM_FALLBACK`** didn't prevent the failures. Both were tried on the F1.
- **More graphics memory kept free on the first rung** (`--fit-target`) moves layers to the CPU, and from 2 GB free the model generates at half speed (5 instead of 8.4 tokens/s).
